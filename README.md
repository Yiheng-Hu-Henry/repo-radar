# repo-radar

给 GitHub 仓库做一次体检，把「这个项目还活着吗、别人敢用吗」压成六个分数和几条具体建议。

零依赖，只用 `urllib` 和标准库。

## 为什么

想知道一个开源项目值不值得用，通常要翻提交历史、数 issue、找 license、看有没有 release —— 五分钟起步，而且很不直观。这个工具把这堆信号压成一张表，并且**每个扣分都写清原因**：分数可以商量，理由不能含糊。

## 安装

```bash
git clone https://github.com/Yiheng-Hu-Henry/repo-radar.git
cd repo-radar
pip install -e .
```

不装也能用：`python -m reporadar check pallets/flask`。

## 用法

```bash
# 单个仓库
reporadar check pallets/flask

# 多个仓库，末尾会附一张排名
reporadar check pallets/flask psf/requests django/django

# 输出 JSON，接到别的脚本里
reporadar check fastapi/fastapi --json

# 同时写一份 Markdown，适合贴到 issue / 周报
reporadar check owner/repo --md report.md

# 也认 URL 和 SSH 写法
reporadar check https://github.com/pallets/flask.git
```

### 关于 token

未认证调用 GitHub API 是 **60 次/小时**，一次体检消耗 5 次（issue 多时 6 次），所以查十来个仓库就会被限流。设置环境变量即可把上限提到 5000：

```bash
export GITHUB_TOKEN=ghp_xxx     # Windows: set GITHUB_TOKEN=ghp_xxx
```

只读公开数据的话，一个不带任何权限的 token 就够了。

## 六个维度

| 维度 | 权重 | 看什么 |
| --- | ---: | --- |
| 活跃度 | 25% | 最近一次提交距今多久、近 90 天提交次数 |
| 社区 | 15% | star / fork / watch 数量（对数尺度，避免大仓库刷满分） |
| issue | 20% | 关闭率、中位关闭时长、积压量 |
| 文档 | 20% | 简介、README 长度、LICENSE、topics、主页 |
| 发布 | 10% | 是否有 release、最近一次多久前 |
| PR | 10% | PR 中位关闭时长、待处理数量 |

总分加权后映射成 A（≥85）/ B（≥70）/ C（≥55）/ D（≥40）/ E 五档。

## 设计说明

**分数必须可解释。** 每个 `Metric` 都带一句 `detail`，形如「关闭率 98%（采样 55 条），中位 1 天内关闭」。用户看到 66 分时能立刻知道是关闭率低还是响应慢 —— 一个说不出理由的分数没有价值。

**star 用对数计分。** 线性映射会让 10 万星的项目直接满分，看不出差异；`15 + 21 * log10(stars + 1)` 让 100 星、1000 星、10000 星分别落在 57 / 78 / 99，区分度保留在真正需要拉开的地方。

**issue 数据是采样，必须标注。** GitHub 没有「历史关闭率」这种聚合字段，只能翻 issue 列表。默认拉两页（200 条，按更新时间排序），所以报告里写的是「采样 N 条」而不是「全部 N 条」—— 大仓库的真实关闭率会被低估或高估，把采样规模摊开说比假装精确好。

**并行拉取。** 一次体检要 5 个接口，串行时从国内访问经常要十几秒。仓库本体单独取（顺便验证存在性），其余四个丢进 `ThreadPoolExecutor` 并发跑，总耗时约等于最慢的那个请求。

**中文对齐不能靠 `len()`。** 终端里一个汉字占两列，`len("活跃度") == 3` 但显示宽度是 6。`render.py` 用 `unicodedata.east_asian_width` 逐字符算宽度，进度条和分数列才能对齐。

## 测试

```bash
python -m unittest discover -s tests -t .
```

52 个用例，全部离线：用固定时间点（2026-11-03）构造 `Snapshot`，验证每个维度的边界、总分与权重之和一致、等级切分、Markdown/JSON 渲染、中文宽度对齐。测试不打网络。

## 局限

- 只有公开指标。代码质量、测试覆盖率、维护者是否友善，这些都测不出来。
- star 数和 issue 数量容易被「运营」影响，分数不是质量证明。
- 私有仓库需要带 `repo` 权限的 token。
